## 何を作ったか

`src/core/marks.ts`（VS Code に依存しない）に、保存形式（`marks.json`）、位置の探し直し（`anchorMark`）、
保存のときの取り直し（`refreshMark`）、AI への依頼の組み立て（`buildAiRequest`）、結果の読み込み

VS Code 側は `src/marks-ui.ts`（装飾、ホバー、ツリービュー、コマンド）で、`src/extension.ts` からは
登録するだけにした。0.1 の `extension.ts` は 300 行ほどで、マーカーの分を足すと倍になるので別のファイルに
分けた（層の規則は同じ: 判断は core、VS Code 側は写すだけ）。設定は `.review-assist.json` の `marks`。

## 位置の探し直しをどう決めたか

計画書は「`quote` と前後の文脈で位置を探し直す（W3C Web Annotation の TextQuoteSelector と同じ考え方）」とだけ
決めていた。TextQuoteSelector を使う実装（Hypothesis の `dom-anchor-text-quote` など）は diff-match-patch の
あいまい一致で探すが、実行時依存を持たない方針なので持ち込まない。代わりに 3 段にした。

1. `quote` が 1 か所にあればそこ
2. 何か所もあれば前後の文脈の一致の長さで選ぶ（同点は保存してある行に近い方）
3. 無ければ「`prefix` と `suffix` が両方そのまま残っていて、その間」。間が空なら（選んだ文を消した）見失う

3 には上限が要る。`prefix` が 1 章目に、`suffix` が 5 章目に見つかったとき、その間を全部「直した後の文」と
呼ぶわけにはいかない。最初は「間の長さが `quote` の何倍まで」と考えたが、その倍率は根拠の無い数になる。
**「間に段落の切れ目（空行）を `quote` より多く含まない」**にした。数を使わずに「同じ段落の中」を言える。
候補が複数なら長さが `quote` に近い方、次に行に近い方。

あいまい一致（編集距離）を入れれば「文脈まで直された文」にも追いつけるが、編集距離のしきい値がまた数になり、
測る対象も増える。まず 3 段で測って、足りなければ考えることにした（下の結果で、見失うのは「選んだ文そのものが
書き直された」ときだけで、取り違えの方が問題として重いと分かったので、足さずに止めた）。

offset ではなく文字列で探すのは計画書の決定どおり。VS Code の装飾の範囲は編集に合わせて動くが、それに頼ると
VS Code の外（git pull、AI、別のエディタ）で直されたときに追えない。

## 前後の文脈の長さを測る

既定値は「測って決める」と計画書にある。測り方を考えた。

**正解をどう決めるか。** `book_mruby3` の git log にある実際の修正を使う。コミット C の親の `.re` で文を選び、
C の `.re` で探し直す。正解は `git diff -U0` の hunk から決まる。

* 文のある行が hunk の外なら、行の対応（hunk の前後の行数の差を足す）で新しい行が決まり、同じ桁が正解
* hunk の中なら、hunk の新しい側の行のどこかに当たれば正解

**どの文を選ぶか。** 地の文（パーサの `lineKinds` が `prose`、見出しを除く）を「。」で切った文を全部。
実際に著者が付けるのは「怪しい文」で、怪しい文ほど直される。だから hunk に入った文の結果を別に数えた。

最初の測り方は hunk に入った文を「文が残る」と「文が直された」の 2 つに分けただけだった。すると「文が直された」の
取り違えが L によらず 70 件で一定だった。一定なのは文脈と関係が無いということなので中身を見ると、
段落を別の場所に移したコミットで、文は消えた hunk ではなく**別の hunk にそのまま現れていた**。
これは正しく追いついているのに、測り方が「元の hunk の中」だけを正解にしていた。「別の hunk に移った」を
分けると、そちらは 61 件全部が正しく、「文が直された」の取り違えは 9 件に減った。

結果（全行は verification）:

| L | 取り違え（行が不変） | 取り違え（文が直された） | 直された文に追いつけた |
|---|---|---|---|
| 0 | 148 | 9 | 0% |
| 8 | 39 | 38 | 31.4% |
| 16 | 24 | 16 | 26.9% |
| 32 | 7 | 9 | 24.0% |
| 64 | 7 | 9 | 21.8% |
| 128 | 7 | 9 | 18.1% |

取り違えは 32 で下げ止まり、追いつける割合は長いほど下がる。**32 にした。**
取り違えの方を重く見た理由: 見失ったマーカーはビューに警告の印で出て著者が気づけるが、取り違えは黙って別の文に
印が移る。

L=32 の取り違え 16 件を `--show-wrong 32` で全部見た。14 件は sub-article の `** Opr: @<code>{B: a(B)}` で、
1 つの記事に同じ行が何度も出て、周りの `** 定義:` の行も似ている。2 件は `porting.re` の短い断片
（`@<hd>{codegen|cg_eval}）。`）が消され、同じ文字列がファイルの別の所にあった。前者は文脈を長くしても
直らない（L=128 でも同じ 7 件）ので、README の「分かっていないこと」に「短い同じ行に付けると移ることがある」と書いた。

「文が直された」2,395 文のうち 1,812 文（L=32）は見失う。これは全 75,499 文の 2.4% で、選んだ文も前後も
書き直されたもの。計画書の「見つからないものは見失ったとしてビューに出し、消さない」で受ける。

測った時間は 1 回 45〜50 秒。`indexOf` で全文を探すので、1 件 0.1 ms ほど（`vm.re` の 679 文で 65〜75 ms）。
打つたびに探し直しても間引きは要らないので、待ち時間の設定は作らなかった（作ればその既定値を測ることになる）。

## 色

計画書は「色は設定に置き、既定値と出どころを書く」。色は好みだが、出どころの無い 16 進を書くのは
「根拠の無い数」と同じなので、借りられる所を探した。VS Code 本体の `merge.currentContentBackground` と
`merge.incomingContentBackground` は「範囲に色を付けて、下の文字と装飾は読ませる」という同じ目的の色で、
明暗のテーマで確かめられている。`editorColors.ts` を取ってきて値を確かめた（基の色 `#40C8AE`・`#40A6FF`、
不透明度 0.5 × 0.4 = 0.2）。どちらをどちらに当てるかは好みなので thresholds に「著者が変えてよい」と書いた。

テーマの色（`ThemeColor`）をそのまま使う案も考えた。数が要らない点では一番よいが、ガターの印は SVG の画像で、
画像の中ではテーマの色が使えない。背景だけテーマの色にしてガターだけ 16 進にすると、テーマによって背景と
印の色がずれる。両方を同じ設定から作る方を採った。

## 依頼ファイル

1 件ごとに id、章、ファイルと行、見出しの道筋、メモ、選んだ文、選んだ所を含む段落と前後 1 段落。
段落は「空行で区切った行の並び」。末尾に結果の JSON の雛形を、id と `quote`（今の原稿の選んだ文）を埋めて付けた。
AI はこれを埋めて書けばよく、`quote` が入っていれば、AI が見た後で原稿が直されたかを拡張が見分けられる
（ホバーに出す。「案を当てる」は確かめてから当てる）。

原稿には ``` を含むコード（Ruby のヒアドキュメントの説明など）があり得るので、囲みの ` は中身の最長の連続より
1 つ長くした（CommonMark の規則）。

## 1 巡やってみて直したこと

のとおりに `../ref/mruby` を読んで結果を書き、CLI で読み直した。

  最後に回した（ビューの `groupMarks` は最初からそうしていたのに、依頼の方で忘れていた）
