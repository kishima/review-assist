# 0.3.0 を著者が Windows で試した後の直し

2026-10-17。著者が 0.3.0 を Windows の VS Code（WSL のリモートの窓。webview は Windows の側で描かれる）で試して、4 つ頼まれた。
バージョンは 0.3.0 のまま（まだ出していない）。実装担当（general-purpose エージェント）が書いた。確かめた結果は
[`../verification/feedback-0.3.0.md`](../verification/feedback-0.3.0.md)。

## 1. 地の文の `@<code>` が本文の明朝で出る

著者の画面では `mrb_state` や `src/vm.c` が本文の書体だった。段階 3 で、コードの `font-family` を「`fonts.code`（Bera Sans Mono、Bitstream Vera Sans Mono、
DejaVu Sans Mono、monospace）＋ `fonts.codeCjk`（Noto Serif CJK JP、…、Yu Mincho、…、serif）」とつないでいた。`family()` は総称（monospace、serif）を
最後に回すので、実際の並びは「等幅の名前 → 明朝の名前 → monospace, serif」になっていた。Windows には等幅の名前がどれも無く、Yu Mincho はある。
Yu Mincho は欧文の字も持っているので、欧文もそこで描かれる。原因は並べ方で、総称を最後に回す処理が、和文のために後ろに置いた明朝を等幅より前にしていた。

直し方: 「等幅の名前 → `var(--vscode-editor-font-family)` → `monospace` → 和文の名前」と組む。総称の `monospace` はどの PC でも何かの等幅に解決される
ので、欧文はそこで止まる。和字は等幅の書体に無ければ後ろへ進む（per-character の fallback）。等幅の名前には Windows の Consolas・Cascadia Mono と
macOS の Menlo を足した。VS Code のエディタの書体を入れたのは、著者が VS Code で選んでいる等幅（既定は Windows で Consolas）が一番なじむため。

確かめ方: この機械（WSL の Chromium）には Windows の書体が無い。同じ状況を作るため、コードの名前を「この機械に無い名前」だけにして開き、
DevTools Protocol の `CSS.getPlatformFontsForNode` で実際に描いた書体を取った（`tools/check-fonts.mjs`）。直す前のビルド（`49ce634`）を
`git worktree` で作って同じ道具で回すと、`@<code>` が Noto Serif CJK JP（本文の書体）になり、著者の見たものが再現した。直した後は monospace まで落ちる。

このとき、もう 1 つ見つかった: 「等幅が全部無い」で、コードの本文（`//list` の中）が Liberation Serif になった。段階 2 の CSS の
`.cm-ra-body-code, .cm-ra-dir-code ~ .cm-ra-body-code` の 2 つ目の選択子がクラス 2 つ分の強さで、段階 3 のテーマの指定（クラス 1 つ）に
勝っていた。段階 3 の書体も大きさも、コードの本文には効いていなかったことになる（既定ではエディタの書体が等幅なので目立たなかった）。2 つ目の
選択子は意味が無いので消し、段階 2 の指定にも `monospace` を足した。

## 2. 参照の札を紙面の形に

著者「『章 HOGEHOGE』は変」。原則は「畳んだ表示は紙面に出るものを出す」。`@<chap>` は `第3章`、`@<hd>` は紙面の形、表などは `表3.1`、脚注は印刷される印。

推測で書かないよう、Re:VIEW 2.5.0 のソース（`lib/review/book/index.rb`、`chapter.rb`、`builder.rb`、`latexbuilder.rb`、`i18n.yml`、`configure.rb`）を
取ってきて読んだ。分かったこと:

* `@<chap>` は `ChapterIndex#number` → `Chapter#format_number` で、CHAPS は `第%d章`、APPENDIX は `付録%pA`（1 → A）。PREDEF・POSTDEF には番号が無く、
  空の文字列が印刷される（札が空では読めないので、そのときだけ題を「」で出すことにした）
* `@<hd>` は `LATEXBuilder#inline_hd_chap`: 章に番号があり、番号の段の数が `secnolevel` 以下なら `「番号 題」`。`secnolevel` の既定は 2（`configure.rb`）、
  `book_mruby3` の `config.yml` は 4。番号は `HeadlineIndex.parse` で、ブロックの中・column の中・題の無い見出しを飛ばし、`[nonum]` は数える
* 表・リスト・図は `Index.parse` の通し番号で、`表` `リスト` `図` ＋ `章の番号.番号`
* 脚注は `LATEXBuilder#inline_fn` が参照の所に `\footnote` を出し、番号は LaTeX が付ける。PDF を見ると p.46 に `*2`（vm の章の 2 つ目の脚注）。
  jsbook は章ごとに数え直して `*N` と印刷する。だから札は「章の中で何番目の `@<fn>` か」

本当に紙面と合うかは、`book_mruby3` のビルドが残している中間の LaTeX（`book_mruby3-pdf/*.tex`）と比べるのが一番確か。表・リスト・図は
`\reviewtableref{3.1}{table:vm:tbl_mrb_state}` のように番号とラベルが並んで出ているので、全部を機械的に突き合わせられる。見出しは `「9.19 EXCEPT、…」`
がそのまま、章は `第2章` がそのまま `.tex` に出ている。`tools/check-printed-refs.mjs` で全部当てて、表・リスト・図 88、見出し 166、章 277、脚注 3 が合った。
PDF でも、参照の直前の文字と札をつないで 23 か所探して全部あった。

最初は札の文字から直前の文字を作るのに `stripInline` を使っていて、`@<chap>{vm}の@<img>{…}` のように直前に別の参照があると「vmの図3.5」を探して見つからなかった
（紙面では「第3章の図3.5」）。札の誤りではなく探し方の誤りなので、直前に命令の無い参照だけを見本にした。

`opcodes` の章は生成物（`contents/opcodes.re`、`insert.rb` が `opcodes_template.re` と sub-article から作る）が紙面の並びなので、番号は生成物を読んで数える。
単体テストの見本では生成物が中身の無い仮のファイルだったので、生成物に無い鍵は元ファイルの並びで数える、という逃げ道を付けた。

参照先の題は札のホバー（`title`）に入れた。

## 3. 「non-basic ASCII」の帯

VS Code は ASCII でない文字の多い文書に帯を出し、全角の記号などに枠を付ける。`contributes.configurationDefaults` の `[review]` で
`editor.unicodeHighlight.nonBasicASCII`・`ambiguousCharacters`・`invisibleCharacters` を false にした。

## 4. 「この節を PDF で開く」がリモートの窓で開けない

`vscode.env.openExternal(file:///…/book.pdf#page=N)` は、WSL のリモートの窓では `vscode-remote:` のリンクに変えられ、Windows はそれを開けない。
著者は「畳んだ編集画面と紙面を横に並べて見比べたい」ので、VS Code の中で、原稿の横に PDF を出すことにした。

* PDF は拡張の側（WSL）で `workspace.fs.readFile` で読み、バイト列を webview に送る。webview（Windows）から PDF のファイルが見えなくてよい。
  ワークスペースのフォルダの URI の形で読むので、手元でも WSL でも SSH でも同じ
* webview は pdf.js（`pdfjs-dist` 4.10 の legacy ビルド）。VS Code 1.85 の Chromium 114 には `Promise.withResolvers` が無く、通常のビルドは動かない
* pdf.js の worker は、webview の中では拡張の資源の URL から直に `new Worker` できない。取ってきて blob: の URL にした（CSP に `worker-src blob:`）
* 全ページの枠を先に並べ（ページの大きさだけ読む）、見えたページから描く（IntersectionObserver）。言われたページの枠へ飛んで、そのページを描く
* 同じ PDF（更新時刻も同じ）なら 2 回目からはページを飛ぶだけ。パネルは裏に回しても中身を保つ（`retainContextWhenHidden`。PDF 2.9 MB を送り直して
  365 ページを並べ直すより軽い）
* 0.2.0 の外のビューアで開く動きは「この節を PDF で開く（外のビューアで）」として残した（手元の窓ではこちらが良い人もいる）

`.vsix` は 192 KB から 718 KB になった。ほとんどが pdf.js（`pdf.worker.min.mjs` 1.4 MB、`pdfview.js` 376 KB、圧縮して 520 KB ほど）。

## 2 回目: PDF が開かない、畳んだ記法の背景

著者が作り直した 0.3.0 を試して、「この節を PDF で開く（横に）」が「PDF を表示できません（Invalid PDF binar…）」になった。PDF は壊れていない。
1 回目の試験（`tools/check-pdfview.mjs`）は通っていた。

試験が見ていなかったのは、拡張（WSL）から webview（Windows）へのメッセージの直列化だった。台の中の `postMessage` は structured clone で、
`Uint8Array` は `Uint8Array` のまま届く。リモートの窓では、`Uint8Array` が JSON を通った `{"0":37,…}` のような形で届くことがあり、pdf.js はそれを
「TypedArray でも文字列でも配列のようなものでもない」と断る。そこで先に、試験に「JSON を通った形で渡す」場合を足し、直す前のビルドで著者と同じ文で
落ちることを見た。

直し方は、バイト列を送るのをやめること。`webview.asWebviewUri` の URL を渡せば、webview は VS Code の資源の読み込みを通して自分で読める。
これはリモートの窓で画像や script を読むのと同じ道で、拡張の資源（`dist/pdfview.js`）がもう同じ道で読めている。pdf.js に URL を渡すと範囲の読み込み
（Range）をするが、VS Code の資源の読み込みがそれに応じるかは分からないので、`fetch` で全体を読んでから渡すことにした（2.9 MB、手元で 0.5 秒ほど）。
`cache: 'no-store'` にしたのは、PDF を作り直しても URL が同じだから。読めなかったときの道として、バイト列で送る形も残し、送る側ではプールの一部を指す
Buffer をちょうどの長さに写し、受ける側では JSON の形も受けるようにした。

畳んだ記法の背景は、VS Code のテーマの `textPreformat.background`（Markdown のプレビューやホバーで地の文の中の `code` に敷く色）を借りた。最初は
`textCodeBlock.background` を考えたが、Light Modern では `#F8F8F8` で白い地の上ではほとんど見えない。`textPreformat.background` は Light Modern で
`#0000001F`、Dark Modern で `#3C3C3C` で、地の文の中の短い部分に敷く色として作られている。古いテーマに無いときのために `textCodeBlock.background` を
後ろに置いた。

この回からの試験は全部 `book_mruby3` の写し（スクラッチに rsync、`.review-assist` を除く）に対して回した。

## 起きたこと: 著者のマーカーのファイルを消した

拡張の側を偽の `vscode` モジュールで動かす試験（スクラッチの台）は、`book_mruby3` に直接マーカーを付けて外す。付けると `book_mruby3/.review-assist/marks.json`
ができるので、試験の後で `rm -rf book_mruby3/.review-assist` で消していた。この回の試験の出力に「AI の結果: marks.json に無い id mmvbobnls」と出て、
`ai-results.json` があったことに気づいた。試験の前に、著者が 0.3.0 を試していた（`contents/vm.re` に著者の編集がある）。**そのとき作った
`.review-assist/`（マーカーと AI の結果）を、試験の後始末で消してしまった。** `.gitignore` 済みのファイルなので git からは戻せない。

VS Code の側の拡張はマーカーを覚えているので、次にマーカーを付ける・外す・済みにすると `marks.json` は書き直される（AI の結果の `ai-results.json` は戻らない）。
以後、偽の `vscode` の試験は `book_mruby3` の写し（スクラッチ、`.review-assist` を除いて rsync）に対して回し、本物の本には書かない。

## 気づいた点

* 試験の道具が本物の本に書くのは危ない（上）。`tools/` の道具（check-editor など）はどれも読むだけだが、マーカーを付ける試験を道具にするなら、
  本の写しを作ってから回す形にすること
