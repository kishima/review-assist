# 0.3.0: 紙面に近い見た目（計画書 段階 3）

2026-10-17。計画書 [`marks-and-editor-plan.md`](../plans/marks-and-editor-plan.md) の段階 3。段階 2（[記法を畳む編集画面](2026-10-17-v0.3.0-editor.md)）の続き。
実装担当（general-purpose エージェント）が書いた。確かめた結果は [`../verification/page.md`](../verification/page.md)。

## 何を決めればよいか

計画書: 「本文の幅、文字の大きさ、行の間、見出し・コード・表の体裁を、本の設定（`config.yml` の `texdocumentclass`、`layouts/`、`sty/` など）から
読める分は読み、読めない分は PDF を測って既定値にする」「書体は本と同じものが PC にあればそれ、無ければ近いもの」。

最初に考えたのは「文字の大きさ」を何に当てるか。紙面は 9pt だが、画面で 9pt（12px）にすると小さすぎるし、VS Code の利用者はエディタの文字の
大きさを自分で決めている。そこで**本文の和文 1 字（1zw）を VS Code のエディタの文字の大きさに当て、ほかは全部 1zw に対する比で決める**ことにした。
これなら紙面の pt は要らず、本文の幅も「全角 N 字」= `N em` で書ける。`texdocumentclass` の `9pt` は読まないことにした（比には効かない）。

## 本の設定から読めたもの

`book_mruby3` の `sty/mytextsize.sty` に `\setlength{\textwidth}{49zw}` がある。Re:VIEW Starter の雛形で、本文の幅を変えるならここを直すと
書いてある。`src/core/booklayout.ts` で `sty/*.sty` からこの形を探す（`%` から後はコメント）。行の送りや見出しの大きさは `jsbook.cls` と
Re:VIEW Starter の `starter.sty` の中で計算されていて（`\mag` や `\Cjascale` が絡む）、読んで再現するのは割に合わないので PDF を測った。

## PDF を測る

PDF から文字の位置と大きさを取る道具が要る。この機械には `pdftotext` も `mutool` も `gs` も無く、Python には `pypdf` だけがあった。
`pypdf` は書体の名前の一覧を取るのに使い、位置と大きさは pdf.js（`pdfjs-dist`）を devDependencies に足して Node で読んだ。pdf.js は
文字の並び（`getTextContent`）ごとに変換行列（大きさと位置）と書体を返す（書体の本当の名前は `getOperatorList` の後の `commonObjs` から）。

`tools/measure-page.mjs` は、本文のページの文字を行（y が同じもの）にまとめ、用途ごとに最頻値を採る。最初の結果で気づいたこと:

* **和文 8.41pt、欧文 9.1pt。** 9pt の本なのに、和文は 9pt でも 9.1pt でもない。jsbook は和文を欧文の 0.924 倍ほどで組む（8.41 ÷ 9.1）。
  CSS では 1 つの書体の並びに 1 つの大きさしか付けられないので、欧文の書体だけを `@font-face` の `size-adjust: 108.2%` で包んで
  紙面の比にした（`unicode-range` で欧文と記号だけ）
* **本文の幅は 412.13pt = 49.0zw。** `sty` の 49zw と合う。ただし `sty/mytextsize.sty` のコメントには「約441pt=155mm」とある。
  PDF では 412pt（145mm）だった（気づいた点）
* 見出しを「題で終わるゴシックの行」で探したら、`==` が 7.57pt と出た。中身を見ると、ページの上の柱（「3.1 VM の起動とデータ構造」）が
  同じ題で終わる細いゴシックだった。太字に限って 12.11pt
* コードの行を「行頭が等幅」で探したら、コードの中の和文が本文と同じ 8.41pt と出た。`@<code>` で始まる地の文の行が混ざっていた。
  本文の大きさの明朝を含む行を外して 7.57pt。表の行の送りも、最初はコードの行（字の大きさが近い）が混ざって 9.84pt と出た。行頭が等幅の行を外して 12.19pt
* 表のセルの大きさは、表の行を見分ける手がかりが無いので、原稿の表のセルで本の中に 1 回しか出ない文字列を PDF で探した（622 のうち 271 が見つかった）

段落の頭の字下げは、後の「改行の位置を比べる」で 1 字ずつずれているのに気づいてから測った（下）。

## 表の列の間（`tableGap`）を測り直す

段階 2 では「見た目で置いた仮の値 2」だった。PDF の表の行を続けて 1 つの表とみなし、行の中で前の文字の終わりから表の 1zw より離れて始まる文字を
セルの始まりとして、列ごとに「前の列の文字の終わりからの距離」の最小（いちばん広いセルの後ろの間）を取った。最頻値は 11.28pt（88 か所のうち 35）。
表の文字の半角（7.57 ÷ 2 = 3.785pt）で割って 2.98、**3** にした。

## 表を実際の書体でそろえる

段階 2 は、セルの幅を半角換算（全角 2）で数えて、等幅の書体で表を出していた。紙面の表は明朝なので、明朝に替えると半角換算ではそろわない。
webview で、セルの見える文字列を canvas の `measureText` で測ることにした。最初に撮った画面では、1 列目（`@<code>{mrb_jmpbuf*}` などの型）だけが
ずれた。セルの文字列を表の書体で測っていたが、`@<code>` の中身は等幅で出ているため。セルをインライン命令ごとに分け、`@<code>` は等幅、参照は札
（札の枠と内側の余白の幅も）で測るようにした。書体の名前と大きさは、隠した見本の行（表の行と同じクラス）を `view.dom` に足して
`getComputedStyle` で取る。書体が後から読み込まれると字の幅が変わるので、`document.fonts.ready` で測り直す。

`fold.ts` は幅の計算をやめ、セルの範囲と列の番号だけを渡すようにした（幅は書体に依存し、書体は webview でしか分からない）。

## 見出しの横のページ番号

既存の `pageIndex`（本の `tools/pdf_pages.py` が作る見出し → ページの JSON）と `lookupPage` を使う。`lookupPage` は見出しが索引に無いと上の段や
章の先頭に落とすが、それを見出しの横に出すとその見出しのページだと誤解されるので、**その見出しの鍵がそのままある見出しだけ**出す（章の題は章のページ）。
`vm.re` では 68 の見出しの全部に付いた。PDF が古いとき（原稿が未保存か、原稿のファイルが PDF より新しい）は薄く出す。計画書は「原稿の方が新しいとき」と
しか言っていないが、未保存の編集も「原稿の方が新しい」に入れた。

## 改行の位置を比べる

計画書は「改行の位置がどれくらい合うかを数える。合わせ込みはしない」。1 つの節で目で数えるより、本全体で機械的に数える方が確かなので
`tools/compare-page.mjs` を書いた。PDF の本文の行をつないだ文字列の中で、編集画面の段落の文字列がそのまま見つかる段落について、
PDF の改行の位置に編集画面の改行があるかを数える。

最初の走行では、編集画面の 1 行の文字数の中央値が 24 と出た（PDF は 53）。画面の行の分け方が誤っていた: 文字ごとの `getClientRects` の上端が
2px 以上下がったら次の行としていたが、同じ行の中でも `@<code>`（字が小さい）と明朝で上端がずれる。行の送りの半分を境にして 55 になった。

結果（全体）: PDF の段落の中の改行 1572 のうち、同じ位置で改行していたのは 134（8.5%）。原因は分かっていて、`book_mruby3` は 1 文ごとに
改行して書いてあり、Re:VIEW は段落の中の改行を詰めて組むのに、編集画面は原稿の改行をそのまま出すため。原稿で 1 行の段落だけに絞ると
7.3%、±1 文字なら 35.8% で、1 文字ずれているものが多かった。PDF を見ると段落の頭が 1 字下がっている（jsbook の `\parindent` = 1zw）。
これは紙面の体裁なので、`measure-page.mjs` で測って（本文の行の左端から 1zw 右で始まる行、897 / 1527）`paragraphIndent` として入れた。
入れた後は、原稿で 1 行の段落で 33.3%、±1 文字で 58.1%、全体で 17.1%。1 行の文字数の中央値は PDF 53、編集画面 54。

字下げを入れたのは「比べて合わなかったから値をいじった」のではなく、比べて気づいた紙面の体裁を 1 つ測って足したもの、と考えた。ほかの差
（欧文の書体がこの機械に無い、LaTeX の和文と欧文の間のアキ、禁則と約物の詰め）は合わせ込みになるので触っていない。原稿の改行を画面で詰める
（行をつないで見せる）と全体の一致は上がるはずだが、カーソルの上下の動きと IME が絡むので、この段階ではやらなかった（計画書の範囲の外）。

並べた画像は 2 節（`images/vm-p37.png`、`images/gc-p84.png`）。PDF を Chromium の pdf.js で描き、PDF の本文の幅と編集画面の本文の幅が
同じ px になる倍率で並べた。pdf.js は file:// では ES モジュールが読めないので、Playwright の `route` で http として配った。

## 書体

PDF に埋め込まれていた書体（`pypdf` で `/BaseFont` を読んだ）: 本文 Noto Serif CJK JP と LM Roman、見出し Noto Sans CJK JP Bold と
Nimbus Sans L Bold、コード Bera Sans Mono。既定の並びは「PDF と同じもの、同じ字形の別名、OS の標準の近いもの」の順にした（`thresholds.md` に理由）。
この機械の Chromium には LM Roman と Nimbus Sans L が無かった。Liberation Sans（Arial・Helvetica と字幅が同じ）を見出しの欧文の並びに足した。

## 気づいた点

* **`book_mruby3/sty/mytextsize.sty:32` のコメント「どちらも約441pt=155mm」と PDF が合わない。** PDF の本文の幅は 412.13pt（145.4mm）。
  49zw の 1zw が PDF では 8.41pt（9pt ではない）なので 49 × 8.41 = 412。コメントは 9pt × 49 で計算したものと思われる。本の側の話（直していない）
* `editor.page` の既定値は `book_mruby3` の PDF から測ったもので、ほかの本（10pt、A5 など）では合わない。`tools/measure-page.mjs` の出力を
  `.review-assist.json` に写す手順は README に書いた。測った値をそのまま設定の形で出す（`--config`）ようにすると楽になる
* 本（mruby の移植の章）の素材になりそうなこと: なし
