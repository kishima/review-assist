## 段階 3: PDF との往復

### 何を作るか

「原稿のこの行が、PDF の何ページか」を出したい。PDF を拡張で解析するのは計画書で捨ててあるので、
**本側で索引 JSON を作り、拡張はそれを引くだけ**にする。分担はこうなった。

| どこ | 何を |
|---|---|
| `book_mruby3/tools/pdf_pages.py`（新規） | PDF と原稿を突き合わせて `{"鍵": ページ}` を作る |
| `book_mruby3/tools/build_pdf.sh` | 配布用 PDF を作ったあとに上を呼ぶ |
| `book_mruby3/tools/drawio2pdf.sh` | 図の PNG（`@<img>` のホバー用）も出す |
| 拡張 `src/core/pdfpages.ts` | 索引 JSON を読み、カーソル位置から鍵を組み立てて引く |
| 拡張 `src/extension.ts` | 引けたら `vscode.env.openExternal` に `file://…#page=N` を渡す |

鍵は段階 1 で決めた Re:VIEW の headline index と同じ形（`章ID` か `章ID|見出しの鍵`、
`../design/review-syntax.md`）。**両側で同じ規則を書く**ことになるので、Python 側の
`parse_headings` は TypeScript の `parseReview` と同じ判断（`==` から数える、ラベルがあれば
ラベル、column の中と題の空のものは入れない、ブロックの中の行は見出しにしない）を写した。
確認は下の「どの見出しからも引ける」で機械的に取ってある。

### PDF から見出しを見つける: 4 回つまずいた

`pypdf` の `extract_text()` は、原稿の文字列とそのままでは一致しない。順につぶした。

**1. 空白。** 組版の字間が抽出テキストでは空白になる（"第 1 章"、"Object と Kernel"、
目次では "5.1 コンパイラの全体像"）。両側から空白を全部落として突き合わせる。

**2. 目次に吸い込まれる。** 目次のページには見出しが全部、しかも本文と同じ順で並んでいる。
最初の実装（見出しを本の順に、ページを前から探す）は目次のページに全部一致してしまい、
566 件が 5〜8 ページ目に張り付いた。**目次の行はリーダーとページ番号で終わる**
（"1.1本書の目的.........9"）のに対し、本文の見出しの行は見出しで終わる。
1 周目の条件を「正規化した行が見出しで**終わる**こと」にしたら分かれた。
ページ全体を目次と判定して外す案も考えたが、行の形で分かれるなら判定は要らない。

**3. 漢字が部首で出る。** "本書の⽬的" の "⽬" は康熙部首 U+2F6C、"⻑い配列リテラル" の
"⻑" は CJK 部首補助 U+2ED1 だった。埋め込みフォントの CID → Unicode の対応がそうなっている。
`unicodedata.normalize('NFKC', ...)` は康熙部首（U+2F00〜）を漢字に写すが、
**CJK 部首補助（U+2E80〜）は写さない**。出てきた 2 字（U+2ED1 → 長、U+2ED8 → 青）を表にして、
`--report` のときは表に無い部首補助の字を数えて知らせるようにした（新しい字が出たら気づける）。

**4. 記号の字形が差し替わる。** 原稿の "／" が "∕"（U+2215 DIVISION SLASH）、"・" が
"‧"（U+2027）で出る。ここで方針を変えた。字ごとの対応表を育てても次の記号で同じことになるので、
**照合の側で記号（Unicode カテゴリ P\* と S\*）を任意の 1 字 `.` にする**ことにした。
漢字・かな・英数は差し替わらないので、そのまま照合しても取りこぼさない。
これで 3 の表は漢字の 2 字だけで済むようになった。

### 見出しの中のインライン命令

`@<chap>{vm}` は "第3 章" に組版されるので、文字列としては一致しない（付録 A の
「レジスタとフレーム（@<chap>{vm}）」が全部これで落ちていた）。見出しの**生の文字列**から
正規表現を組み立てることにした。番号になる命令（`chap` `hd` `list` `table` `img` `fn` …）は
`.+?`、`@<br>{}` は空、それ以外（`@<code>` など）は中身をそのまま。原稿の見出しで実際に
使われているのは `@<chap>` 13 件と `@<br>` 9 件だけだった（`grep '^=' | grep -o '@<[a-z]*>'`）。

`@<br>{}` の入った見出し（参考文献の書名と著者）は組版で 2 行に分かれるので、行単位では
当たらない。**2 周目**として「目次でないページの、行をつないだ文字列に含まれる」で探し直す。
章の題「mruby Operation Code Reference」も 2 行に折り返されていて、ここで当たった。

### 結果

```
$ python3 tools/pdf_pages.py --report
pdf_pages: book_mruby3-pages.json に 576 件（見出し 576 のうち 行 566、折り返し 10、見つからず 0）
```

**576 件すべてページが取れた。** 詰めていった経過は 549 →（部首 2 字）571 → 573 →
（記号を任意の 1 字に）576。所要は 5.6 秒（361 ページ、2.9 MB の PDF）。

正しさは PDF の目次（しおり）と突き合わせて確かめた。`pypdf` の `reader.outline` には
141 件（章と `==` の節まで。`===` 以下は `tocdepth` の外）の飛び先ページが入っている。
本の順に並べて突き合わせたところ **132 件が一致、食い違い 0**（残り 9 件は、しおりの文字列が
"A.2 レジスタとフレーム（第3 章）" のように組版後なので、この突き合わせ方では対応が取れなかった分。
索引としては取れている）。しおりを索引そのものに使う案は、**141 件しか無く `===` 以下が
入らない**ので採らなかった。

### 出力先を変えた

計画書は `book_mruby3-pdf/pages.json`（PDF の中間ファイルの隣）と書いていたが、
**そこには書けなかった**。`book_mruby3-pdf/` は `kauplan/review2.5` のコンテナが root で作るので、
ホストの python3 から書くと `PermissionError` になる。PDF の隣という意図は同じなので、
`book_mruby3.pdf` と並ぶ `book_mruby3-pages.json`（`.gitignore` 済み）にした。
`bookname` から作るので、著者が本の名前を変えても追従する。

### 図の PNG: drawio と gs を測って gs にした

計画書は「`drawio -x -f png -s 2` か、既存の PDF を gs で描画。どちらが速くきれいかを試して決める」。
2026-09-19 に両方動かした。

| 方法 | 時間 | 容量 | 作れる枚数 |
|---|---|---|---|
| `drawio -x -f png -s 2 --crop` | 1 枚 2.3 秒（39 枚で約 90 秒） | 1 枚 96 KB | 39（`.drawio` のある分だけ） |
| gs（コンテナ内、`-r150`） | 57 枚で 14.8 秒 | 合計 30 MB | **57（全部）** |

見た目はどちらも読める（`gc_states` で見比べた。drawio 版のほうがわずかに輪郭が硬い）。
決め手は速さより**枚数**で、初版から引き継いだ図 18 枚には `.drawio` が無い（2019 年に Excel で
作った PDF しか残っていない）。PDF から描けば全部が同じ経路で揃うので gs を採った。
gs はホストに入っていないので、PDF ビルドと同じ `kauplan/review2.5` の中のものを使う。
`--user "$(id -u):$(id -g)"` を付けないと、コンテナの root が書いた PNG をホストから
上書きできなくなる（`book_mruby3-pdf/` で踏んだのと同じ穴）。

解像度 150dpi は、本文幅 155mm いっぱいの図が約 915 px になる値。VS Code のホバーの幅は
それより狭いので、300dpi にしても見え方は変わらず容量だけ増える（同じ 57 枚で 79 MB、70 秒）。
容量の 30 MB はほとんどが初版の図 2 枚（`afterword/fabgl.png` 23 MB、`blockdiagram.png` 4.5 MB。
元が写真入りの大きな PDF）で、残り 55 枚は 1 枚 40〜140 KB である。git 管理外なので困らない。

### 拡張側

判断は `src/core/pdfpages.ts` に置いて、`src/extension.ts` は「引けた／引けなかった」を
メッセージと `openExternal` に写すだけにした（段階 1・2 と同じ分け方）。

索引に無い見出しのときに何も言わずに諦めるのは使いにくいので、**上の段へ落とす**ようにした。
`first|導入|細かい話` が無ければ `first|導入`、それも無ければ章の先頭 `first`。
本を組んだあとに節を足した状態でも、その節の近くが開く。落ちた先は出力チャンネルに書く。

開けない理由は全部メッセージで言う（計画書の「索引 JSON が無い・見出しが無いときはメッセージで
理由を言う」）。設定 `pdf` が無い／PDF が無い／設定 `pageIndex` が無い／索引ファイルが無い／
索引が壊れている／このファイルが章に属していない／鍵が索引に無い、の 7 通り。

### 確認

`test/pdfpages.test.js`（9 件）で索引の読み込み・鍵の組み立て・落とし方を見ている。
実物の原稿に対しては `test/book_mruby3.test.js` に 2 件足した。

* **図 39 枚すべてで `imagePreview` の PNG が解決する**（`//image` の id → `images/png/<章>/<id>.png`
  が実在する）
* **見出し 576 すべてで、その行から `lookupPage` がページを返す**。しかも全部が見出しそのもので
  当たっている（章の先頭に落ちた見出しが 0 件。これが 0 なら、Python 側と TypeScript 側の
  鍵の作り方が食い違っていないということになる）

どちらも本側の生成物が要るので、無ければ飛ばす（GitHub の CI では飛ぶ）。

`tools/build_pdf.sh` を通しで 1 回（約 4 分）。`OK: 2895957 bytes written` /
`Overfull hbox: 0` / `pdf_pages: … 576 件` で、`.re` に差分は出ていない。

## 段階 4: 配布

### GitHub Actions

`.github/workflows/ci.yml`。push と PR で `npm ci` → `npm test` → `npm run build` →
`npm run package`、できた `.vsix` を artifact に上げる。タグ `v*` のときだけ Release を作って
`.vsix` を付ける。

Release を作るのに第三者の action（`softprops/action-gh-release` など）は使わず、
runner に最初から入っている `gh release create` にした。増やす依存は少ないほうがよい。

push の対象は `main` とタグだけにした。枝は PR で回る。両方を `'**'` にすると、PR のある枝で
同じものが 2 回回る。

`.vsix` に `.github/` が入ってしまっていた（9 ファイルが 10 になった）ので `.vscodeignore` に
1 行足した。中身は `dist/*.js` とマニフェストだけに戻っている。

`npm run build` は計画書（と依頼）の名前に合わせて `package.json` の `compile` を改名したもの
（中身は `node esbuild.mjs` のまま）。`watch` と `typecheck` はそのまま。

### README と CHANGELOG

README に「Release から `.vsix` を落として `code --install-extension`」を足し（今までは
clone して自分で `npm run package` する手順しか書いていなかった）、設定の表に `pdf` と
`pageIndex` を、機能の表とコマンドの表に「この節を PDF で開く」を足した。
「分かっていない・やらないこと」に、**VS Code 実機での確認が限られている**ことを書いた
（Extension Development Host が使えない環境で作っているため。段階 1・2 から変わっていない）。

CHANGELOG は 0.1.0 に段階 3 の分を足した。`package.json` の `version` は 0.1.0 のまま。

## 決めなかったこと（著者へ）

* **`file://…#page=N` が実機でページまで開くか**は確かめていない。`vscode.env.openExternal` は
  URI を OS の既定のアプリに渡すだけで、`#page=` を読むかどうかはビューア側の約束
  （Adobe の open parameters。Chrome / Edge / Firefox / Preview は読む）。
  Linux で既定が evince のときは読まない、という報告がある。実機で見て、駄目なら
  「ビューアのコマンドを設定で指定する」形に変える余地がある
* CI に `npm run typecheck` を入れていない（依頼に挙がっていた 4 つだけにした）。
  `npm run build` は esbuild なので**型は見ていない**。型の誤りを CI で止めたいなら 1 行足す
* `unreferenced-table` は 8 件のまま（段階 1・2 の記録では 13 件。著者が 5 本に `@<table>` を
  足した）。残りを消すか `warnUnreferencedTables: false` にするかは著者の判断
