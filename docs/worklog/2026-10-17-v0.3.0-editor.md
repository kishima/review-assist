2026-10-17。計画書 [`marks-and-editor-plan.md`](../plans/marks-and-editor-plan.md) の段階 2。著者は同日「計画を最後まで実装して」。

## 何を作ったか

`.re` を「Review Assist（記法を畳む）」という CustomTextEditor で開けるようにした。中身は webview の CodeMirror 6 で、
`.re` の文字列をそのまま文書として持ち、記法の印を装飾で隠す。カーソルを入れた記法だけ元の書き方に戻る
（Obsidian や Typora の「ライブプレビュー」と同じ考え方）。

* `src/core/fold.ts`: どこを畳むかの一覧（`planFolds`）。`parser.ts` の結果から作る
* `src/core/editing.ts`: 囲む（`wrapInline`）、ブロックの雛形、候補の型
* `src/core/editor-data.ts`: 拡張から送るもの（参照の札、候補、図のパス、マーカーの位置）と、webview の編集を文字列に当てる `applyTextChanges`
* `src/core/editor-config.ts`、`editor-protocol.ts`: 設定 `editor` とやりとりの型
* `src/webview/editor.ts`、`style.ts`: CodeMirror 6 の画面（`dist/webview.js`）
* `src/editor-ui.ts`: CustomTextEditorProvider と TextDocument との同期、コマンド
* `src/marks-ui.ts`: マーカーのコマンドが編集画面の選択でも動くように（`EditorBridge`）
* `tools/check-editor.mjs`、`check-editor-sync.mjs`、`editor-harness.html`: Chromium で確かめる台

## どこまでを webview で決めるか

計画書は「webview 側に要る形（範囲と種類の一覧）は `core` で作って送る」。素直に読むと、拡張の側で一覧を作って
postMessage で送ることになる。それだと 1 文字打つたびに「webview → 拡張（編集）→ 拡張で解析 → webview（一覧）」の
往復が要り、その間の装飾は 1 つ前の文字列のものになる。カーソルが記法に触れたかどうかで見た目が変わる画面で、
1 往復分ずれた装飾が出るのは困る。

一覧を作る `fold.ts` を `src/core/` に置き（VS Code に依存しない、テストできる）、**それを webview の束にも入れる**ことにした。
`fold.ts` が読む `parser.ts` と `width.ts` はファイルシステムに触らないので、そのままブラウザで動く。これなら「core で作る」
「パーサを 3 つ目にしない」を守ったまま、往復なしで今の文字列から装飾を作れる。索引を引かないと決まらないもの
（`@<hd>` の札に出す見出しの題、候補、図の場所）だけを拡張から送る。

このために `src/core/` の型の置き場所を少し動かした。設定の型（`EditorConfig`）は `config.ts`（`node:fs` を読む）にあると
webview の型検査が `node:fs` まで辿ってしまうので `editor-config.ts` に、札の型（`RefLabel`）は `editor-data.ts`（索引を読む）
から `editor-protocol.ts` に移した。webview の `tsconfig.json` を別に作って DOM の型をそちらだけに入れたので、拡張の側で
DOM を触る書き間違いは型で止まる。

## パーサに箇条を足した

0.1 のパーサは箇条（` * ` など）を見ていなかった（索引と診断に要らないため）。畳むには要る。`fold.ts` の中で正規表現を
書くと「3 つ目のパーサ」の始まりになるので、`parser.ts` に `listItems` を足した。形は推測せず、Re:VIEW 2.5.0 の
`lib/review/compiler.rb`（`compile_block` の分岐、247〜251 行）を取ってきて確かめた: ` * ` は `\A\s+\*`（`*` の後の
空白は要らない）、` 1. ` は `\A\s+\d+\.`、` : ` は `\A\s*:\s`（行頭の空白は無くてよい）。最初は 3 つとも「行頭の空白と、
印の後の空白が要る」と思い込んで書いていて、取ってきた本物と違っていたので直した。

表も同じく `lib/review/builder.rb` の `Builder#table` を読んだ。セルは `line.strip.split(/\t+/)`（タブがいくつ並んでも 1 つの区切り）、
頭の `.` は落とす、区切りの行は `/\A[\=\-]{12}/`（12 文字以上の `-` か `=`）、**区切りの行が無い表は 1 列目が見出し**。
最後のは知らなかったので、見出しを太字にする所に入れた。雛形の区切りの行も 12 文字にした。

## 畳み方

計画書の表のとおり。決めたこと:

* **記法が出る条件。** インライン命令は、選択のどれかがその範囲に「触れて」いるとき（端を含む）。端を含めないと、`}` の直後に
  カーソルを置いても畳まれたままで、矢印キーで中に入れない（隠した範囲はカーソルが飛び越える）。行の記法（見出し、箇条、
  ブロックの頭、`//}`、表の区切り）は、カーソルがその行にあるとき
* **ブロックの頭の行は札（ウィジェット）で置き換える。** その行の中のインライン命令（キャプションの `@<code>`）は、
  札が覆っている間は畳まない（重なった置き換えを作らない）。カーソルが頭の行にあれば頭は元の書き方に戻り、キャプションの
  インライン命令は地の文と同じ規則で畳む
* **図は行を置き換えず、行の下に足す。** 最初は `//image` の行をまるごと図（ブロックのウィジェット）で置き換えるつもりだったが、
  CodeMirror ではブロックで置き換えた行には矢印キーでカーソルが入れない（前後に飛ぶ）。頭の行は普通の札にして、図は行末の
  後ろに `block: true` のウィジェットとして足した。これなら行にカーソルを置ける
* **表はタブを広げてそろえる。** 計画書は「表として表示し、セルの中を編集できる」。表を HTML の `<table>` のウィジェットにすると、
  セルを編集するにはセルの中に別の編集器を入れることになり、IME と取り消しが絡んで大きくなる。そこで文字列はそのままにして、
  タブ（の並び）だけを幅のある空白（`PadWidget`）で置き換え、列の最も広いセルにそろえた。幅は `width.ts` の半角換算
  （全角 2）を `ch` で、行は等幅の書体。セルはただの文字なので IME も取り消しもそのまま効く。CSS の `tab-size` を表の幅に
  する案も考えたが、`tab-size` は全部の列が同じ幅になる（いちばん広い列に合う）ので捨てた。タブは記法というより区切りなので、
  カーソルがその行にあってもそろえたままにした（打つ間に列が動かない）
* **箇条の深さを全角の空白で表す。** ` ** ` は `　•`。CSS の字下げの幅を決めると新しい数になるので、文字の幅で表した
  （折り返した 2 行目はぶら下がらない。段階 3 の仕事）
* **コードの中のインライン命令は畳まない。** Re:VIEW は `//list` の中の `@<b>` も解釈するが、構文の色付け（0.1.2）と同じく
  コードとして読めることを優先した。`book_mruby3` ではコードの中に 0 件

数（色、大きさ、幅）: 色は全部 VS Code のテーマの CSS 変数。見出しの大きさは HTML の h1〜h5 の既定（仕様を取ってきて値を
確かめた。最初「15.3.7」と書いたが、今の仕様では「15.3.6 Sections and headings」だったので直した）。表の列の間 `tableGap` だけは
出どころが無く、見た目で置いた仮の値と `thresholds.md` に書いた。CSS の罫線や余白の数は設定にせず、そのことを `thresholds.md` に書いた。

## TextDocument との同期

計画書は「`TextDocument` と双方向に同期し（`WorkspaceEdit`）、保存・取り消し・dirty の印は VS Code のものを使う」。
VS Code の CustomTextEditor の見本（catScratch）は、変更のたびに全文を webview に送り直す。表示だけならそれでよいが、
打っている最中に自分の編集が全文で返ってくると、カーソルと IME が乱れる。

* webview の編集はトランザクションごとに番号を付けて送り、拡張は順に当てて `ack` を返す。自分の編集を当てている間の
  変更の通知は送り返さない
* 外からの変更（取り消し、普通のエディタ、ディスク、「案を当てる」）だけ全文で送り、webview は共通の頭と尻を残して間だけ置き換える
* 位置は行と桁で送る。通しの位置（offset）で送る案は、CodeMirror が行の切れ目を 1 文字と数え、
  VS Code が CRLF を 2 文字と数えるので、CRLF の原稿で 1 行ごとに 1 ずつずれるため捨てた。行と桁なら両方で同じ（行の中身は同じ）。
  CodeMirror の `lineSeparator` を原稿の改行に合わせたので、`sliceDoc()` が元のファイルと同じ文字列を返す
* 拡張の側は「webview が持っているはずの文字列」（`mirror`）も追い、当てた結果と比べる。食い違えば全文を送る（保険）
* 行き違い: webview にまだ `ack` の来ていない編集があるときに外からの変更が来たら、そのまま当てると、拡張の側で後から当たる
  webview の編集と二重になったり、片方だけになったりする。すぐには当てず、`ack` が揃ってから `sync` を頼んで全文をもらい直す
  （正は TextDocument）。`check-editor-sync.mjs` の 3 でこの順を作って確かめた
* マーカーと診断の位置は、拡張が当て終えた番号と一緒に送る。webview はその番号より後の自分の編集（まだ `ack` の来ていないもの）
  で位置を写す。打っている間に印が 1 文字ずつずれるのを防ぐため。`check-editor-sync.mjs` の 4 で、`ack` 前に 1 行足してから古い番号の
  マーカーを送り、足した行の分だけ下に出ることを見た
* 取り消しは VS Code のもの。CodeMirror の `history` を入れると取り消しの履歴が 2 つになる（webview の取り消しで戻した文字列が
  また WorkspaceEdit として VS Code の履歴に積まれる）ので入れなかった。VS Code の webview は `Ctrl+Z` を自分で受けて
  取り消しのコマンドを回すはずだが、CustomTextEditor でそれが TextDocument の取り消しになるかは実機でしか確かめられない
  （README の「確かめ方」4）

拡張から送る札・図・マーカーは、前と同じなら送らないようにした。webview は受けるたびに装飾を作り直す
（`vm.re` で 1 回 3 ms ほど。`dispatch` の 4 ms から `planFolds` の 1.4 ms を引いた見積もり）ので、1 文字ごとに同じものを受けると無駄になる。

## マーカーとコマンド

0.2.0 のマーカーのコマンドは `vscode.window.activeTextEditor` の選択を見ていた。編集画面が前にあるとき `activeTextEditor` は
無いので、`marks-ui.ts` に `EditorBridge` の口を作り、編集画面（`editor-ui.ts`）が今の文書と選択を渡すようにした。
webview は選択が変わるたびに行と桁を送っている。「マーカーを開く」「案を当てる」の最後で普通のエディタを開いていた所は、
編集画面で開いていればそちらで選ぶようにした（2 枚目のエディタを開かない）。

右クリックのメニューは `webview/context`（VS Code 1.70 から）。`data-vscode-context` を body に付けた。キーの割り当ては
0.2.0 と同じく既定を持たず、README に例を書いた（編集画面が前のときは `editorLangId` が立たないので `activeCustomEditorId` を使う）。

## 確かめ方

### Chromium で全章

webview は `acquireVsCodeApi` が無ければ送るものを配列に溜めるようにして、`tools/editor-harness.html` で開ける形にした。
`check-editor.mjs` は `book_mruby3` の 57 本を 1 本ずつ流し込み、畳んだ項目ごとに「カーソルを別の行に置いたときの行の DOM の文字」
と「その項目の中に置いたときの文字」を比べる（17,307 か所）。

最初の走行で 2 か所だけ「外」で行の DOM が見つからなかった（`extension.re` 761 行と `overview.re` 437 行の `//}`）。
まず、中身を全部隠した行では `view.domAtPos` が前の行の終わりを返すのだと思い、行の DOM を「行の頭の位置」で探すように
直したが、まだ見つからない。DOM を書き出してみると、その行は `cm-gap`（CodeMirror が描かない部分）の中だった。
確かめる前に「その位置が描く範囲（`view.viewport`）に入っているか」を見ていたが、入っていても範囲のちょうど端で、
カーソルを動かした拍子に CodeMirror が描く範囲を詰め直していた。表示の誤りではなく確かめ方の誤りなので、行が見つからなければ
その行を真ん中に寄せてから見直すようにした。これで 0 件。

記法の数を数える所では、生成物の `contents/opcodes.re` を数えると sub-article の中身が二重になるので外した。
数えた結果は `grep` で数えた数（`@<code>` 9,091、`//list` 208 など）と合った。`@<embed>` は `grep` で 2 件あるのに畳んだ数に出ない。
調べると 2 件とも `#@#` の行の中（コメント）で、パーサが拾わない。正しい。

### 拡張の側

Extension Development Host は使えないので、`check-editor-sync.mjs` で拡張の側（`editor-ui.ts`）の手順を Node で真似して
webview とのやりとりを見た。さらに 0.2.0 と同じく偽の `vscode` モジュールで `dist/extension.js` を動かし、provider に偽の
TextDocument と webview を繋いで、`ready` → `init`、`edit` → `WorkspaceEdit` → `ack`、外からの変更 → `text`、編集画面の選択で
マーカーを付ける、ホバーのボタンでコマンド、を通した（偽の `vscode` はスクラッチに置き、repo には入れていない。
VS Code の API を真似た 120 行ほどの台で、本物とずれても気づけないため）。この中で付けたマーカーのために `book_mruby3/.review-assist/`
ができたので消した。

### 遅さ

1 文字打つごとに `planFolds`（解析を含む）を回し直し、装飾を全部作り直している。範囲を絞る（見えている所だけ作る）工夫は、
測ってから考えることにした。Playwright の本物のキー入力で、`keydown` から CodeMirror の更新が終わるまで `vm.re` で中央値 4.4〜4.8 ms、
最大 13.5〜14.6 ms。生成物の `opcodes.re`（287 KB）でも中央値 8.2〜8.5 ms。1 フレームに収まるので、絞る工夫も間引きの待ち時間も
入れなかった（待ち時間を入れればその既定値をまた測ることになる）。

最初の測り方は `keydown` の中で `setTimeout(0)` を置き、その時刻を「処理の終わり」としていた。中央値が 10.6 ms と出たが、
`view.dispatch` 1 回は 4 ms で、差が大きすぎる。Playwright の `press` は keydown・keypress・input・keyup を別々に送るので、
`setTimeout` は CodeMirror の処理ではなくキーの一連の後に回っていた。CodeMirror の updateListener から時刻を取るように直した
（webview に測るための口 `__reviewAssistOnUpdate` を足した。VS Code の中では使わない）。

## 確かめられなかったこと

VS Code の実機（特に日本語 IME、`Ctrl+Z`、保存、右クリック、編集画面 ⇔ 普通のエディタ、テーマの色）。README の「確かめ方（0.3.0）」に 15 の手順。

IME は CodeMirror 6 が composition を自分で扱う。心配は、変換の途中でこちらの装飾が変わること（打っている所はカーソルが触れているので
畳まれないが、同じ行の別の記法は畳んだまま。ブロックの頭の行で打つと行全体が元に戻る）。CodeMirror は composition 中の DOM を守るが、
こちらの装飾の作り直しと絡んだときの挙動は実機で見るしかない。
