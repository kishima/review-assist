# 2026-09-20 0.1.2 — 構文の色付けを自前で持つ

## 出発点

著者の VS Code には Re:VIEW の色付け用に `atsushieno.language-review` 0.7.5 が入っている。
この拡張は `.re` と**同じディレクトリ**の `catalog.yml` しか見ない。

```js
// ~/.vscode-server/extensions/atsushieno.language-review-0.7.5/out/src/preview.js:143
const catalogYamlFileName = path.resolve(docDirName, "catalog.yml");
const books = fs.existsSync(catalogYamlFileName) ? getChapters(...) :
    { predef: [], contents: [], appendix: [], postdef: [] };
```

`book_mruby3` は `.re` を `contents/` に移し、`catalog.yml` は根に置いたままなので、
`contents/` に `catalog.yml` は無く、`books` が空の 4 本になる。すると「この文書は
catalog のどこにも属さない」と判定され、他章への参照すべてに
「参照先 chapter の overview が見つかりません。」が出る。診断だけを切る設定は無い。

そこで色付けを review-assist 側に持たせ、language-review を無効にできるようにする、
というのがこの版の目的である。

同じ言語 ID に文法が 2 つあると何が起きるかも確かめた。language-review の `package.json` は

```json
"languages": [{ "id": "review", "extensions": [".re"], "configuration": "./review.configuration.json" }],
"grammars": [{ "language": "review", "scopeName": "text.review", "path": "./syntaxes/review.tmLanguage" }]
```

で、こちらは scopeName `source.review`。VS Code は 1 つの言語に 1 つの文法しか使わないので、
**両方を入れたままだとどちらが勝つか決まらない**。README には「無効にする」と書いた。
`unwantedRecommendations` は勧めるのをやめるだけで無効にはしないので、そこも書き分けた。

文法は自前で書いた。language-review の文法は Apache-2.0、この拡張は MIT なので、
写すとライセンスが揃わない。読んではいるが 1 行も持ってきていない。

## 2. コード系ブロックの中でインライン命令を色付けしない判断

Re:VIEW は `//list` `//emlist` の中でも `@<...>` を解釈する。だから「忠実に」やるなら
コードブロックの中でもインライン命令を色付けするべきである。そうしなかった。

理由は 2 つ。1 つは読みやすさで、C のコードには `<` `>` `{` `}` が大量に出るので、
その一部がインライン命令の切れ目に見えるとコードとして読みにくい。
もう 1 つは、**この原稿ではどちらでも何も変わらない**こと。数えた。

```
$ awk '/^\/\/(list|listnum|emlist|emlistnum|cmd|source|terminal)/{inb=1;next}
       /^\/\/}$/{inb=0} inb&&/@</{n++} END{print n+0}' $FILES
0
```

コード系ブロック 487 個（list 329 + emlist 131 + cmd 27）の中に `@<` は 1 つも無い。
忠実さを取っても見た目は 1 文字も変わらないので、読みやすい方を選んだ。

キャプション（`//list[id][caption]`）の中では色付けする。キャプションは地の文で、
拡張の他の部分（`rules` の `scope: "prose"` がキャプションを地の文として見る）とも揃う。

判断が変わる条件も書いておく: 原稿がコードブロックの中で `@<b>` を使い始めたら、
`#block-code-id` / `#block-code` の `patterns` に `#inline` を入れる（1 行）。

## 3. scope 名の選び方

`docs/design/syntax-highlight.md` に表で残した。決め方は「テーマが色を持っている前置きを使う」で、
`markup.heading.N` は VS Code 同梱の Markdown 文法、`markup.raw.block` も同じ、
`meta.separator` は ini / shell の文法が区切り行に使っている。

迷ったのは 2 つ。

**ラベルと id を同じ scope にするか。** 見出しの `{chap_SEND}` とブロックの `//list[id]` は、
どちらも「別の場所から参照される名前の定義側」なので `entity.name.label.review` で揃えた。
別にする案もあったが、読む人にとっては同じものなので分ける理由が無い。

**索引（`@<hidx>`）をどうするか。** `@<hidx>{Fiber}` は本文に何も出さない。地の文と同じ色だと
読むときに本文と混ざる（vm.re の冒頭は `@<hidx>` が 5 つ並ぶ行がある）。かといって
コメント扱いにするのは嘘なので、`markup.other.index.review` という**既定のテーマが色を持たない**
名前にした。そのままだと地の文と同じに見えるが、`editor.tokenColorCustomizations` で薄くできる。
「薄くする」のは拡張ではなくテーマの仕事なので、ここで止めた。

`@<bib>` `@<eq>` を参照系に入れなかったのは、この拡張が参照として解決していないから
（README の「やらないこと」）。色だけ参照に見せると、F12 が効かないのに効きそうに見える。

## 4. 文法のテストに何を使うか

依存を増やしたくないので、まず増やさずに済む道を探した。

* **`vscode-tmgrammar-test`** — 専用のツールで書きやすいが、`.re` のテストファイルに
  `# ^^^ scope` の行を書く方式で、原稿の実在の行をそのまま材料にしにくい。依存も重い
* **自前で正規表現を回す** — 文法の正規表現を JSON から取り出して自分で当てる。依存 0 だが、
  それは「VS Code と同じ結果になるか」を確かめていない。`begin`/`end` の入れ子や
  `captures` の中の `patterns` を自分で実装し直すことになり、**確かめたいものを自作することになる**
* **`vscode-textmate` + `vscode-oniguruma`** — VS Code 本体が文法を読むのに使っている当のライブラリ。
  ここで出るトークンはエディタで付く scope と同じ

3 つ目にした。devDependencies が 2 つ増えるが、

* `.vsix` には入らない（`npm run package` の出力は 11 ファイル 55.87 KB で、`dist/*.js` と
  `syntaxes/` と `language-configuration.json` だけ）
* Extension Development Host が無いこの環境で、**文法を機械で確かめられる唯一の方法**である。
  0.1.0 から「確かめられるのは `src/core/` だけ」という制約を抱えてきたが、文法については
  これで外れる

ので釣り合うと判断した。`test/grammar-helper.js` に 60 行ほどの口を書いて、
`test/grammar.test.js` から使う。

assert の形は「この行のこの scope が付いている範囲の文字列は、ちょうどこれ」にした。

```js
assert.deepStrictEqual(textsWithScope(tok, text, 'markup.raw.inline.review'), ['R[a] = R[b]']);
```

範囲を数字で書くより読みやすく、原稿の行をそのまま貼れる。

## 5. 取りこぼしの機械確認

個別の assert は「書いた規則が効いているか」しか見ない。書き忘れた規則は見つからない。
そこで網を 1 枚置いた: **原稿の `@<` と `//` の出現のうち、根の scope（`source.review`）しか
付いていないものを数える**。

`contents/vm.re`（`@<` 1461 個、`//` 120 個）をテストに入れてある。

```
$ npm test
✔ 文法: contents/vm.re 全体で、scope の付かない @< と // が無い (28.063159ms)
# tests 103
# pass 103
# fail 0
```

手で 57 ファイル全部に掛けた結果も 0 件だった。

```
$ node scratch/sweep.js
files=57 lines=20680 "@<"=13132 "//"=1371 unscoped=0
```

この網が本当に仕事をしているかを、壊して確かめた。最後の受け皿である `#inline-other`
（知らないインライン命令を受ける規則）を外すと、

```
files=57 lines=20680 "@<"=13132 "//"=1371 unscoped=77
```

77 件に増える（`@<br>` `@<href>` `@<embed>` のうち地の文にあるもの）。戻すと 0 に戻る。
網は機能している。

なお、この数え方ではコード系ブロックの中の `@<` は「`markup.raw.block.review` が付いている」
ので取りこぼしに数えない。上に書いたとおり `book_mruby3` のコードブロックに `@<` は 0 個なので、
この違いはこの原稿では出ない。

## 残っている不確かさ

**実機の見た目は確かめていない。** 0.1.0 から同じで、この環境に Extension Development Host が無い。
scope が正しく付くことは VS Code と同じエンジンで確かめたが、著者のテーマでそれが
読みやすい色になるかは、`.vsix` を入れて見るまで分からない。特に

* `markup.other.index.review`（`@<hidx>`）は既定のテーマで色が付かない。地の文と同じに見える
* `meta.separator.table.review`（表の区切り行）も、テーマによっては色が付かない

の 2 つは「色が付かない」が想定どおりの動作なので、見て物足りなければ
`editor.tokenColorCustomizations` で足すことになる。

**`//graph` `//embed` `//raw` の中身**は、原稿に無いので本文と同じ規則で色付けしてしまう。
gnuplot や生の LaTeX が地の文の色になるが、使い始めたら直す。
